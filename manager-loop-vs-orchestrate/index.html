三件事先講。

一、貼文裡的「Manager Loop」與論文裡的機制是兩個東西，是搜尋摘要把它們黏起來的。對論文 HTML、abs、PDF 全文與 GitHub README 四處跑 grep -i "manager[ _-]?loop"，全部回 0；論文自己的詞是 Manage-Execute-Audit (MEA) loop。但兩者不是無關——它們是同一個底層 pattern 的獨立實例。

二、貼文說「一週內建構了完美無瑕的曼哈頓」，而作者自己的長文說它還在進行中。「完美無瑕」與「建構了」是轉述時加上去的。

三、真正值得看的不是曼哈頓，是那篇論文——它的三角色分工與你的四閘高度重疊，而它有兩樣你沒有的牙齒。

還有第四件，是異質票逼出來的：你這個委託本身接受了貼文的因果敘事。貼文是三件套（新模型、Manager Loop、遊戲引擎），而委託只把中間那一件抽出來研究。這件事寫在下面第三節。

Manager Loop 是一個人的工程實務，不是一套發表過的方法

它出自 Matt Shumer 2026-09-03 的貼文與同期的個人 review 頁。

定義是他自己下的，逐字：

"I'm calling this the Manager Loop: one agent keeps the project moving, while another does the work."

形狀是三句話。coordinator 先訪談使用者直到目標達成共識，把目標變成一份 checklist。

然後在另一個 Codex session 起一個 implementer——他特別強調那不是 sub-agent：

"It turns that into a checklist of to-dos, then starts an implementer in a separate Codex session… a completely separate agent, not a sub-agent."

"The implementer is not the coordinator's sub-agent."

兩者之間只傳兩樣東西，他畫成 Phase + goal → 與 ← Completion + evidence。

coordinator 用 goal mode 讓 implementer 持續朝該階段的終點線工作，做完就推進下一個階段。

它疊在既有的東西上，不是憑空的。往上追是 Ralph Wiggum loop（Geoffrey Huntley，2025 年中）：while :; do cat PROMPT.md | agent ; done，記憶不放 context、放檔案系統與 git 歷史。

作者自己標的限制，逐字兩句：「I still wouldn't call long-running autonomous work solved.」／「Ambitious long runs still need lots of coordination and can asymptote if they aren't set up very carefully.」

那個 asymptote（趨近水平、再怎麼跑也上不去）是他自己的用詞，不是我加的批評。

論文那套的三個角色，每一個都被拿掉了某樣東西

LongHorizon-Harness（2026-08-03 投稿，29 頁）把一輪拆成三段，而分工的關鍵不在誰做什麼，在誰被禁止做什麼。

兩句逐字引文承載了整套設計的重量：

"The report oi describes the executor's outcome but does not establish that the contract has been completed."

"audit conclusions must be supported by evidence obtained directly from the environment rather than by the executor's completion claim."

你的系統裡有一句話跟它幾乎同義：執行者的「我做完了」是意圖不是事實。兩邊獨立寫下同一件事。

稽核前拍快照harness 在稽核期間監看工作區，偵測到 auditor 改動就還原，並記成完整性違規；那份報告不得支撐「已完成」。
三行控制頭auditor 的輸出必須有可被程式解析的 Status:／Integrity:／Contract audit: 三行，缺頭整份不採信、不從內文猜。
task state 沒有 schema論文寫得像結構化記錄（requirement／artifact／fact 加四態），實作裡是 manager 每輪重寫的一段自然語言，只有小節順序被規定。

四條該搬、四條不該搬，其中兩條被異質票改寫過

  • 該搬 ①·已被異質票改寫先決定模式切換規則，再談要不要把 fresh-context 提到監督式預設。我原本寫的是「直接提上來」。盲審票把它改了，理由成立且更準：你的自主段已經長得像精簡版的 Manager Loop（短 context、ledger 當磁碟記憶、goal-based 單 session），而 Manager Loop 的預設迴圈長得像你明文只准在人不在場時用的那一檔。它逐字問：「你要比的是兩套系統，還是同一套系統裡的兩種模式？」本系統既有位置：Skills/orchestrate/SKILL.md:481。⚠ 這意味著你已經有兩種模式，但沒有寫下切換規則——那才是缺口。支撐 fresh-context 的機制證據（Chroma 18 模型、退化在 context 沒滿時就開始）不變，變的是它該落在哪。
  • 該搬 ②讓驗收者看環境本身，不是看執行者的報告。MEA 的 auditor 拿不到 executor 的原始軌跡，只能自己去看檔案、視窗、日誌。你的 review agent 拿到的通常是 subagent 的轉述——而你自己的教訓庫裡已經記過摘要會丟掉會翻轉結論的那一段。本系統既有位置：閘四「驗收永遠主 session 外部跑」。缺的是「看什麼」的規定。
  • 該搬 ③驗收者自己被改過的東西不算數。MEA 在稽核期間監看工作區，auditor 動了就記完整性違規、報告作廢。你的七道收官閘沒有任何一道在問「跑這道閘的過程有沒有改到被驗的東西」。查無。這是本次比對找到的最乾淨的缺口。
  • 該搬 ④驗收輸出要有機器可解析的控制頭，缺頭整份不採信。MEA 的 auditor 必須交出三行固定格式，harness 逐字寫著「不會從內文猜」。你的閘目前驗的是欄位在不在——而你自己已經量到，那擋得住「整步消失」、擋不住「填表過閘」。控制頭不解決後者，但它把「格式對了」變成可程式判定的前提。本系統既有位置：form_routing_check.py 等七道閘。這是強化不是新增。
  • 不該搬 ⑤·問題被異質票拆細了「換成獨立 session」是問錯粒度——先問你要隔離哪一層。盲審票把它拆成三層：〔行程／session〕〔工作記憶／context〕〔裁決權：誰有權宣布完成〕。Manager Loop 把前兩層捆在同一個獨立 session 上；你只有第三層（主控端外部驗收），而 session 層查無。它逐字警告：不拆開的話，「你會以為要抄 A 的 session 模型才能得到 B 想要的『不信自報』，或以為 B 已經有 A 的隔離」。維持不搬的理由不變（換獨立 session 會丟掉 Agent tool 的完成通知，而你已量到檔案輪詢當完成訊號是假的）。但這條現在是待決策不是已否決——你要的若只是第二層，有比換 session 更便宜的做法。
  • 不該搬 ⑧·異質票獨有把委派額度推到 96 路。這一軸我完全沒看到，是盲審票撈出來的，而它的論證我判成立：你的驗收不變式是「每條通過帶可指認證據指針、每輪至少一票異質審核」，而那個不變式的負載單位是「這輪被宣稱通過的判準」，不是葉節點任務數。它逐字：「96 路並行會讓指針變成抽樣劇場……你的停損數的是輪次與判準通過數淨增，數不到『swarm 內部互相覆蓋、最後交一份綠的』。」查無對應計數單位。這是本次比對找到的第二個乾淨缺口，而且方向與直覺相反——它不是你該加的能力，是你該拒絕的能力。
  • 不該搬 ⑥用同一個底層模型當 auditor。論文預設三個角色同一個 backbone，而且它說明了理由——逐字「ensuring that the comparison reflects the effect of task-state management rather than differences in model capability」。那是實驗控制變因，不是生產建議。照搬會讓 auditor 繼承 executor 的盲點。你的異質票紀律在這一格是對的。本系統既有位置：閘四「至少一票非 Claude 家族」。不動。
  • 不該搬 ⑦輪數上限 25。論文的任務是可逆的桌面操作，多跑幾輪成本只是 token。你的迴圈會碰不可逆動作，而且你有「連兩輪無淨增就停」這個邊際偵測——那比一個固定大數字更適合你的任務類型。本系統既有位置：閘三。不動。

盲審票對你系統的四個指控，其中一個是選擇效應

第一票拿到的是兩份去識別化材料，不知道哪一份是我方的，也沒拿到我的預判。它對兩邊各列了盲點。以下四條是它對你的系統提的，我逐條判過。

  • 成立·而且最重凍結判準會系統性懲罰探索性工作，而這個代價從系統內部看起來像「治理的必要成本」。它逐字：「軟體（以及 B 自己列入的研究／投資）常有『做過一輪才知道判準寫錯了』……設計者不容易看見自己在篩選『開跑前就能寫死完成條件』的任務。」這是選擇效應不是機制錯誤——被篩掉的任務不會出現在任何 ledger 上，所以沒有任何讀數會顯示它。
  • 成立異質票的規格仍然是同一份任務文本。它逐字：「相關失敗若寫在任務裡（共同的錯誤世界模型、共同的假證據型態），攻堅票會用同一副眼鏡。」★ 這一條在本輪被當場證實：本輪唯一沒有被指定對象的那一票（第二票），抓到的東西最大。第一票預測了它，第二票演示了它。
  • 部分成立·待驗短回合本身也會造出假完成。它的論證：你的監督式關掉連續自跑、預設 3 輪，而「被打斷的實作交出來的 ledger 指針仍可 exit 0……驗收看到的可能是短回合拼出來的表面綠」。機制講得通，但它沒有讀數，我也沒有。列為待驗，不列為已知缺陷。
  • 已被既有條文涵蓋「執行者是不是獨立 session」沒成為協定條款。這條與上面「不該搬 ⑤」是同一件事，已在那裡處理。重複列出會讓缺口數看起來比實際多。

而所有這些「該搬」與「盲點」都要先過一道篩子，那道篩子本輪不存在。

第二票逐字：「差異不是缺口。沒有『我現在死在哪』當篩子，每一列都同樣有趣，也就同樣不必動。」

它問了你一題，我照抄：「你這套系統最近一次真正失敗或卡住，是哪一件事？用實例講。」——這題答不出來，上面那四條該搬沒有落地點。

那些數字要怎麼讀

論文最漂亮的一組是 WeaveBench 上 51.8 → 80.7。這一組是同模型對照——同一個 Qwen 3.7-Plus，一邊跑原生 harness、一邊跑 LongHorizon，作者自跑，可比。

但另外幾組不是。OSWorld 2.0 的 baseline 是官方報告值，而工具面不對等。

LongHorizon 用 GUI 加 CLI 的混合工具池，官方 baseline 逐字「typically rely only on GUI actions」。WeaveBench 的官方最佳參考點也不是 matched，作者自標「Our runs use root privileges inside the task virtual machine, whereas the official results use a regular user account」。

還有一個論文自己的內部不一致。摘要寫 from 20.0% to 34.3%，正文表格與附錄寫 20.6 → 35.3。我親自把全文抓下來 grep，六個數字全部存在於文件裡。我照抄不調和。

成本那一格更值得看，因為它推翻了「加稽核就是固定加幾倍」這個直覺。

三個 benchmark 上分別是 2.3×、3.6×、以及少 24%。論文自己的解釋是：強模型能用更少的稽核與重規劃輪次滿足契約，弱模型得花額外推理反覆執行與復原。稽核本身在三個 benchmark 上吃掉 19.4% 到 38.1% 的 token。

關鍵前提這三套解的不是同一個問題。把它們並排比「誰比較完整」會得到錯的答案——軸 1 就分家了。

三件事必須明說。

一、Manager Loop 那半的證據基礎就是一個人的自述。沒有第三方複現、沒有技術細節、沒有可跑的程式碼。我能做的最強驗證是取到原文並確認它確實是那個帳號在那個時間寫的——那證明貼文為真，不證明貼文的內容為真。
