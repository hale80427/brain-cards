你沒指定的維度，agent 會自己選

Andrew Ng 在 2026-08-28 發了一篇談軟體工程基本功的長文。它的結論不是「還是要學寫程式」，而是一句更難的話——你要懂到能指定取捨，甚至要先知道有哪些取捨可以指定。

BLUF

不懂軟體基本功的人，用 coding agent 一樣做得出能跑的東西。真正的代價不在那裡。

代價在延遲、可用性、一致性、可靠性、可維護性、簡潔性、成本這七個維度上——agent 必須落點，你沒指定它就自己選了，而你不知道那裡曾經有一道選擇題。

定位

這是一張技能地圖的第二格，不是一篇勸學文

發文當下的讀數是讚 6133、轉推 981、回覆 178、瀏覽 573776。

它不是獨立的一篇。Andrew Ng 與團隊做了一張 AI Engineering Skills Map，切成四大項，這篇處理第二項。第一項（建構與部署 AI 應用）已經發過，後兩項還沒。

所以讀這篇的正確姿勢是：它在補一張圖的其中一格，不是在寫一份完整的職涯建議。

機制

不懂基本功的代價，是那道選擇題你根本沒看見

全篇最重的一段在開頭，值得逐字看：

A novice who vibe codes without understanding software fundamentals can create simple applications, but this often leads to the coding agent making bad tradeoffs in latency, availability, consistency, reliability, maintainability, simplicity, and/or cost. In such cases, the developer didn't know such tradeoffs even existed and therefore did not steer the agent to make the right decisions for their application context.

拆開來看，這裡有一個容易被讀漏的轉折。他沒有說「做不出來」。他明講簡單應用照樣做得出來。失效的形式是做出來了，而且看起來沒事。

為什麼「多寫幾個專案就會了」解不掉這件事？因為練習修正的是做得對不對，而這裡的問題發生在更早一層——你不知道有一件事該被做。缺的不是實作能力，是取捨清單的可見性。

拿一個具體的例子。一個做得出來的內部工具，可能在毫無提示的情況下把使用者狀態放進記憶體、而不是持久層。demo 正常，一個人用正常，直到重啟或第二個人進來。

工程師不會覺得這是自己的判斷失誤，因為他從未意識到「狀態放哪裡」是一個要他回答的問題。

他不知道那些取捨存在，所以沒有去指揮 agent。

拆解

五項子能力不是並列的清單，它們有先後

原文用五個小節展開軟體工程基本功。表面上是並列，讀完會發現它們互相墊著。

子能力它其實在問什麼最容易被低估的一句
建全端應用你懂不懂前後端各層在做什麼agentic coding 讓專才可以擔全端，但補的是熟悉度，不是判斷力
管理資料存什麼、存多久、用什麼型態存地基相對難改，即使 agent 會幫你做遷移
設計系統架構各層懂了之後，怎麼拼起來正確架構是移動標靶，原型的架構撐不到生產
讓系統安全且可靠怎麼設計失敗，以及誰負責安全資安左移之後，多數開發者同時是半個資安工程師

機制

資料架構選錯不會報錯，它只是安靜地少給 AI 一段脈絡

這是全篇唯一給出新機制的一句，而它被埋在第二個小節的中段：

Your AI systems will get their own input context from your data source, so if data architecture is chosen poorly, the AI doesn't know what it doesn't know.

把它拆成三步。第一步，AI 系統的輸入脈絡是從你的資料源長出來的。第二步，資料架構決定了哪些東西進得了那個脈絡。

第三步——也是真正麻煩的那一步——缺漏不會變成訊號。

一個具體的樣子。一份只存最終結論、不存推導過程的知識庫，接上檢索之後看起來運作良好。它答得出「結論是什麼」，答不出「為什麼當初排除了另一個選項」——而後者才是複用時真正要問的。

使用者不會收到錯誤訊息，只會慢慢覺得這套東西沒那麼好用，卻說不出哪裡壞。

這個結構在別的地方也見過。某個欄位長期為零，看起來像「這件事沒發生過」，實際是那條路徑上根本沒有裝儀器。零讀數與沒有儀器，在紀錄上逐字相同。

資料架構的缺漏在 AI 端也是這樣——「它沒提到」與「它拿不到」，在輸出上無法區分。

Andrew Ng 在這裡補了一句時效警告，值得一起收：為 agent（而不是為傳統軟體、也不是為人）設計資料基礎設施，本身是快速演化中的領域。也就是說，這一格的最佳實踐現在還在動。

操作

把七個維度變成派工前要補的七句話

原文停在「你要懂到能指定」，沒有往下寫怎麼指定。這一節是本文的延伸，不是原文內容：把那七個維度各翻成一句可以直接寫進指令的話。

Andrew Ng 的收尾也值得逐字放著：

Some parts of coding knowledge — like memorizing coding syntax — are becoming obsolete. But developers who deeply understand how software works vastly outperform those who vibe code without understanding.

記語法過時，懂運作方式的人大幅勝出。這句話本身沒有新意——真正有內容的是前面那條機制：勝出的方式，是他看得見那些別人看不見的選擇題。

邊界

這篇的證據強度，撐不起「研究顯示」四個字

把它當一份有品味的職能盤點骨架可以，當實證結論不行。三個具體的地方：

一、沒有樣本、沒有對照組、沒有引用。作者的措辭是 this often leads to 這一類。整篇是個人經驗歸納，不是量測。

二、那七個維度是他列的。沒有任何地方說明這份清單是怎麼來的，也沒有檢驗它是否窮盡。少一個維度，前面那條「你看不見的選擇題」的論證強度就掉一塊。

三、Skills Map 的方法論至今未公開。系列前一篇只說地圖來自職缺分析、專家訪談與問卷，沒有給樣本數、抽樣方式、職缺來源地區與時間範圍。這一點決定它是能力盤點的外部基準，還是一份有品味的個人意見。
