本機端 LLM 的需求端全景——用可控性換前沿性

BLUF

在本機跑大語言模型，需求的本質是「用可控性換前沿性」：使用者離開雲端 API，換取隱私主權、可預測成本、離線與客製自由，代價是自己承接硬體與運維。

關鍵轉折是——開放權重與前沿模型的差距，已從「代差」收斂為「時間差」（約 3–6 個月），本機「夠用」的邊界大幅擴張。功能廣度與工具鏈都不再是瓶頸，真正的需求缺口落在 UX 剛需（記憶持久化、模型切換、本地整合）。

但這條邊界的精確座標（tokens/s、回本月數、逐 GPU 級距）在本次查證中高度分歧、不可信——本報告給方向、不給假精度，被否決的數字集中列於文末誠信段。

一、核心張力：為什麼要離開雲端？

需求端的第一問是「為什麼不直接用雲端 API」。驅動力不是單一原因，而是一條從剛性強制到個人偏好的光譜。搞混這條光譜的層級，就會把「偏好」誤當「必須」。

層級驅動力底層機制
剛性層
（法遵強制）		隱私與資料主權HIPAA 無 BAA 的醫療、嚴格落地的金融、政府主權合約。關鍵在 CLOUD Act——美國供應商即使把機房設在歐盟，仍受美國司法管轄，故雲端「即使加密」也無法滿足真主權，air-gapped 本機部署成為唯一解
結構層可預測成本、離線可用消除按 token 計費的變動稅（token tax），成本從營運費轉為一次性資本支出；離線環境（無網、機敏場域）雲端根本不可達
偏好層客製化／微調自由、模型可換可自由換模型、微調權重、改 system prompt，不受供應商政策與版本更迭綁定

產品定位本身就印證了這個驅動核心：Jan 的官方標語是「100% offline on your computer」，LocalAI 自我定位為「self-hosted, local-first alternative to OpenAI, Claude」——「隱私 ＋ 雲端替代」被開源社群當成第一賣點寫進 tagline。

矛盾點（別把偏好誤當強制）

「必須本機」只對「無 BAA／真資料主權」這個子集是絕對的。HIPAA 本身其實沒有資料落地要求（屬合約性義務）；純粹的資料落地情境，有時用主權雲（sovereign cloud）就能替代。把偏好層的理由（省錢、想玩）講成剛性強制，是需求評估最常見的自我欺騙。

二、功能廣度已不是瓶頸

三年前「本機模型能做什麼」還是一份短清單。到 2026 年 7 月，開放權重模型已在每一個功能面向都有對應的成熟選項——「做得到」不再是限制條件。

功能面向代表開放權重模型
對話 / 通用推理Llama、Qwen3、DeepSeek、Mistral、Gemma、Phi 系列
CodingQwen3-Coder（Apache 2.0）
視覺多模態Qwen3-VL、MiniCPM-V
語音 / 音訊Whisper-large-v3
RAG / EmbeddingQwen3-Embedding / Reranker（MTEB 多語榜第一）
關鍵事實：差距是「時間差」不是「代差」

據 Epoch AI 的 Capabilities Index（一手研究來源，非行銷部落格）：開放權重與封閉前沿的能力差距，2023 至 2025 平均約 3 個月、2026 年起約 4 個月；公開 benchmark 落在約 4–6 個月，私有 held-out benchmark 則約 8–10 個月。換言之，本機模型不是「弱一個世代」，而是「晚半年」。這正是本機夠用邊界擴張的根因。

限定條件：「覆蓋」指的是存在性——每個面向都有可用模型，不等於與雲端頂規品質平價。最前沿的複雜推理鏈、最新的多模態能力，雲端仍領先約半年。

三、應用場景盤點

把功能落到具體場景，本機在個人／家庭伺服器規模的成熟度分佈如下：

場景本機成熟度說明
個人生產力成熟對話、摘要、改寫、翻譯——中小模型已足堪日常
軟體開發成熟Qwen3-Coder 級模型可做補全、重構、除錯輔助
本地文件 / 第二大腦成熟（工具就緒）RAGFlow、WeKnora 等開源 RAG 引擎可全本機建知識庫
隱私敏感工作本機的主場法務、醫療、財務、機敏研發——資料不出本機是核心價值
離線環境本機獨佔無網、機敏場域，雲端不可達
7×24 背景 agent可行但證據薄家庭伺服器常駐 tool-calling 自動化——工具存在，長時間可靠度缺實測佐證

本地 RAG 知識庫具體長什麼樣

這對你的第二大腦場景最相關。兩套已被一手 GitHub README 逐字佐證的開源方案：

  • RAGFlow（infiniflow）：融合 RAG 與 Agent 能力的開源引擎，具深度文件理解，能解析 Word／slides／Excel／txt／圖片／掃描檔／結構化資料／網頁，採 template-based chunking 與「多路召回 ＋ 融合 re-ranking」。
  • WeKnora（騰訊）：可用 Ollama 本地模型同時當 LLM 與 embedding 後端，支援 Local／Docker／Kubernetes 私有離線部署，達成完整資料主權。
待驗缺口

現有證據只到「功能存在」——個人第二大腦規模（數千至數萬份文件）下的召回品質、embedding 選型、繁體中文處理效果缺乏實測數據。這是要親自跑一次才知道的，不能靠部落格背書。

四、不可或缺的體驗（UX 剛需）

這是需求端最硬、也最被低估的部分。功能廣度與工具鏈都成熟後，本機 LLM 的真正差異化不在「能不能跑」，而在「用起來順不順」。以下六項是社群反覆點名的剛需：

1. 記憶持久化——最痛的缺口

本機 runner（LM Studio、llama.cpp）每次開新 session 都從空白起，缺少雲端 Projects／Gems 那種「自動載入背景」的機制，使用者被迫一次次重新交代脈絡（re-brief）。這是 XDA 等社群媒體反覆抱怨的頭號痛點——不是模型不夠聰明，是它「記不住昨天」。

2. 模型切換

依任務一鍵換模型：日常用快的小模型、難題換大模型、coding 換專用模型。切換的摩擦力直接決定使用頻率。

3. context 管理

長對話的視窗管理——什麼進 context、什麼被截斷，需要可見可控。

4. 本地檔案與工具整合

能讀本機檔案、呼叫本機工具（tool-calling / function-calling），模型才從「聊天框」變成「能幹活的 agent」。

5. 隱私可見性

本機的價值主張是「資料沒外流」，但這個價值要「看得到」才成立——使用者需要能感知、能驗證資料確實留在本機，否則隱私只是口號。

6. 易用性分水嶺

一鍵安裝（Ollama 一行指令、LM Studio 圖形介面）vs 手動編譯（llama.cpp）——這條線決定觸及誰。技術門檻不是中性的，它直接篩選使用者群。

誠信標註：回應速度

速度是 UX 的一級變數，互動流暢與否有主觀門檻。但本次研究中所有具體 tokens/s 數字全被對抗式驗證否決（詳見文末），因為它與硬體 × 量化 × 併發強耦合、跨來源分歧劇烈。所以這裡只能說「速度很關鍵」，不能給你一個可信的門檻數字——要精確值只有在目標機實測一條路。

五、工具鏈三層地圖

本機 LLM 生態清楚分成三層。理解分層才能對場景選對工具，而不是被工具名稱淹沒。

層角色代表工具
平台層給人直接用Ollama、LM Studio、Jan、LocalAI
引擎層負責跑得快llama.cpp、vLLM、MLX-LM、TensorRT-LLM
UI 前端對話介面Open WebUI、Lobe Chat、SillyTavern

依場景選型

  • 單人原型 / 快速上手 → Ollama（一行安裝，最低摩擦）
  • GUI 優先的 Mac／Windows 使用者 → LM Studio（內建 HuggingFace 瀏覽器與量化建議）
  • 多使用者 / 常駐服務 → vLLM（PagedAttention ＋ continuous batching，高併發吞吐遠勝單機 runner，這是家庭伺服器要服務多裝置時的分水嶺）
  • 嵌入式 / 邊緣 → llama.cpp（工廠、IoT、離線最輕量）
框架精修

三層是巢狀不是並列——Ollama／LM Studio 實際上是把 llama.cpp／MLX 包裝成引擎再套介面。所以正確心智模型是「平台騎在引擎之上」，而非三者乾淨並排。這決定了你在哪一層調效能。

六、硬體門檻（可量化的部分）

硬體需求有一部分是可以用第一性原理精確估算的，這部分可信；另一部分（跑多快）不可信，留到誠信段。

VRAM 估算公式

VRAM ≈ 參數量(十億) × 每權重位元組數，其中 FP16 = ×2、FP8 = ×1、INT4 = ×0.5。所以 INT4 量化把記憶體壓到 FP16 的 1/4。實例：Phi-4 14B 在 INT4 下純權重約 7GB，單張 RTX 4090（24GB）有大量餘裕。

限定：這條公式只估「權重」記憶體，實際總 VRAM 還要再加約 15–20% 給 KV cache、activation 與框架 overhead。

等級配置能跑到
可用底線16GB RAM ＋ 8GB VRAM ＋ 100GB+ SSD7B 級模型
建議甜蜜點32GB RAM ＋ 24GB VRAM（RTX 3090／4090）單張 24GB 卡的天花板約 34B（Q4_K_M）
大模型入場需 40–48GB VRAM70B（Q4_K_M，單張消費卡不夠，需多卡或大 unified memory）

這張表只到「裝不裝得下」（VRAM 容量）層級，這部分經多來源交叉佐證可信。逐 GPU 級距的完整對照表、逐型號的 tokens/s，在查證中被否決——那些數字是分歧噪音，不列入。

七、本機 vs 雲端：決策邊界（方向性）

什麼時候該本機、什麼時候該上雲，有一組方向性啟發（medium 信心，非精算）：

走雲端，如果……走本機，如果……
零星使用（月花 < US$30）月花 US$80+（重度使用）
要最佳模型品質處理敏感／專有資料
要最新多模態（視覺／音訊）要可預測成本
不想管硬體要離線可用
誠信標註

US$30／US$80 是方向性門檻，不是硬事實，且假設你已擁有硬體。更精細的成本破局點（回本 5.8–6.7 個月、US$500–700 門檻、18–24 個月回本）在對抗驗證中全數陣亡。這組邊界只能當「往哪個方向想」的啟發，不能當精算依據。

八、本研究的邊界與誠信段

這一段是整份報告最該讀的部分之一。本次 deep-research 抽取 117 條主張、對其中 25 條做三票對抗式查證，結果 14 條確認、11 條被否決。被否決的主張幾乎全部集中在同一類：精確數字。

被對抗式驗證否決的主張（不採信）

  • 所有具體 tokens/s 分層（CPU 10–25、RTX 4090 130–160、Apple Silicon 45–120、各工具 40–12,500……）——跨來源分歧劇烈，多數 0–3 票全滅
  • 成本回本精算（5.8–6.7 個月、US$500–700 門檻、18–24 個月）
  • 逐 GPU 的 VRAM 級距對照表（RTX 3060／3090／5090／Mac Studio 逐級距）
  • 「MLX 是 Apple Silicon 最快路徑、Ollama 底層已改用 MLX」的主張
  • 品質差距的具體百分點（本機 7B HumanEval 45–55% vs 前沿 90%）
方法論啟示

本機 LLM 領域的「數字」是最不可信的一層——因為它與硬體 × 量化 × 併發強耦合，而部落格級來源之間互相抄襲、缺一手實測。要拿到可信的效能與成本數字，只有一條路：在你自己的目標硬體上實測。這恰好是「建本機運算單元」能做的第一件正事——先建 benchmark。

四個實測缺口（open questions）

  1. 目標硬體（RTX 4090／5090、Mac Studio M 系列）跑主流開放權重模型的真實 tokens/s——互動流暢門檻的關鍵
  2. 7×24 背景常駐 agent 的實務可靠度、記憶持久化與 context 管理方案
  3. Apple Silicon unified memory 路徑（MLX vs llama.cpp Metal）的真實效能定位，以及大 unified memory 跑 100B+ 模型的實用性
  4. 本機 RAG 在個人第二大腦規模的召回品質與繁中文件處理效果

對你的落地啟示

你們近期在建本機運算單元，這份需求端盤點指向三個結論：

  • 「能不能跑」已經是解決的問題。功能廣度不缺、工具鏈成熟、硬體門檻可估算。把精力放在「能不能跑」上是打過去的仗。
  • 真正的差異化在 UX 剛需。記憶持久化、模型切換、本地檔案與工具整合、隱私可見性——這些是產品與體驗要下功夫的地方，也是雲端替代品目前做得最差、本機最有機會贏的縫隙。
  • 所有效能與回本數字，別信報告別信部落格。用你們的機器實測。這不只是嚴謹，更是你們建運算單元的第一個可交付成果——一份針對自己硬體的 benchmark，比任何二手數字都值錢。
