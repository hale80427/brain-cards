迴路工程：讓 AI 代理人自己推進任務

BLUF

迴路工程的核心，是把人類反覆下提示的工作，改成一套會排程、分工、檢查、記錄、再決定下一步的小系統。

一句話先講清楚

過去使用 AI 寫程式，常見做法是人類一輪一輪下提示：你給上下文，AI 回答，你讀完後再補下一句。迴路工程把這件事往上抽一層：人類開始設計一個會反覆運作的系統。它會找工作、分派任務、檢查結果、記錄狀態，然後再決定下一步。

白話說：你從開車的人，變成設計物流線的人。這條線會自己派車、檢查路況、回報結果。

為什麼這件事現在浮出水面

Addy Osmani 把迴路工程視為代理 harness 工程的延伸。Harness 是讓單一代理人能穩定執行任務的環境；迴路則在 harness 上面再加一層節奏與治理。它讓代理人被放進一個會持續運轉的工作流，而非只被叫來做一件事。

這個概念之所以變得實用，是因為 Claude Code 與 Codex 這類工具已經把許多原語放進產品裡。以前要靠 bash 腳本、cron、臨時資料夾與人工維護；現在，排程、目標迭代、子代理、worktree、skill 都開始成為工具本身的一部分。

你不應該再提示程式碼代理人了。你應該設計能提示你的代理人的迴路。 — @steipete，Addy Osmani 貼文中引用
我不再提示 Claude 了。我有正在運行的迴路在提示 Claude 並決定該做什麼。我的工作就是撰寫這些迴路。 — @bcherny，Addy Osmani 貼文中引用

一個迴路需要的五個元件

  1. 自動化：像心跳一樣定期觸發，讓系統自己找出待處理工作。
  2. 工作樹：讓多個代理人各自有獨立 checkout，避免改到同一批檔案。
  3. 技能：把專案知識寫成可重用的指令與參考資料，代理人不用每次重猜。
  4. 外掛與連接器：讓代理人能接上 issue tracker、CI、文件、repo 與其他工具。
  5. 子代理：一個代理人提出解法，另一個代理人檢查，降低自評失準。
第六個元件是記憶。它可以是 Markdown、Linear 看板或 repo 內的狀態檔。重點是：狀態要留在單次對話之外，否則模型下一輪就會忘。

元件怎麼接成迴路

迴路需要清楚的接線方式。排程先喚醒系統，系統用 skill 讀懂專案規則，再把工作丟進隔離的 worktree。代理人做完後，子代理或測試條件檢查結果。通過就記錄；沒通過就回到下一輪。

階段系統在做什麼人類要看什麼
發現掃 issue、CI、待辦或 repo 變化它找出的工作是否真的值得做
分派建立 worktree，載入 skill，交給代理人任務範圍是否小到可 review
執行代理人修改程式、文件或測試是否遵守專案慣例
驗證跑測試、lint，或由子代理檢查停止條件是否可被驗證
記錄寫下完成事項與下一步狀態是否留在對話之外

真正的風險：成本、品質與理解負債

Addy Osmani 在原文中保留態度，這點很重要。迴路看起來會提高速度，但速度也會放大錯誤。如果 token 很充足，代理人可能跑得很遠；如果 token 不足，它可能偷省步驟。成本與品質會一起變成系統設計問題。

  • Token 成本：迴路會反覆呼叫模型，成本曲線可能比單次提示陡很多。
  • 品質下滑：如果驗證條件太弱，系統會產生看似完成但其實粗糙的輸出。
  • 編排稅：多個代理人平行工作後，人類 review 變成瓶頸。
  • 意圖負債：迴路跑久後，系統可能開始偏離原本想達成的事。
  • 理解負債：人類若只看結果，不看推進過程，最後會失去判斷力。
這篇貼文的證據強度屬 Tier 2：高經驗權重，但缺少可獨立驗證的量化對照。它適合當作實務框架，不適合直接當成已確立事實。

如果要實作，先從小迴路開始

最安全的起點，是挑低風險、可驗證、可回滾的工作。例子包括每日 issue 分類、CI 失敗摘要、文件同步、測試覆蓋缺口掃描，或小型 refactor 候選清單。

  1. 先定義停止條件：例如測試通過、lint 乾淨、只產出候選清單。
  2. 把專案規則寫成 skill：避免代理人每次靠猜。
  3. 用 worktree 隔離修改：讓失敗成本可控。
  4. 加一個獨立檢查者：測試、子代理或人工 review 都可以。
  5. 把狀態寫到 repo 或看板：避免每次從空白上下文重來。
判準很簡單：如果某個任務沒有清楚的驗證方式，就不要先放進自動迴路。
