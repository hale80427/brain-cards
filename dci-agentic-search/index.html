當代理夠強，檢索器反而成了瓶頸

一篇用 grep 打贏 RAG 的論文 ｜ arXiv 2605.05242 解讀

BLUF

當大型語言模型代理（LLM agent）夠強的時候，傳統的嵌入向量檢索器（embedding retriever）反而會變成代理式搜尋（agentic search）的瓶頸。

讓代理直接用 grep、bash 這些命令列工具操作原始的語料庫（corpus），這個做法叫做「直接語料互動」（Direct Corpus Interaction, DCI）。

結果：更準、更便宜，而且不用事先建任何索引。

重點不是「grep 萬能」，是介面解析度

這不是「grep 萬能」的口號。論文用嚴謹實驗加上消融分析（ablation）得出的結論是：

檢索品質取決於「介面解析度」（interface resolution），而不只是嵌入向量的相似度高不高。

傳統的檢索增強生成（RAG）把所有需求壓縮成一次 top-k 相似度查詢。代理看到的，只是檢索器決定翻出來給它看的那幾筆。

DCI 不一樣。它把語料庫打開成一個可以自由探索的環境，讓代理可以：

  • 執行精確的字面搜尋（lexical search）
  • 在文件局部做上下文驗證
  • 多步修正自己的假設

這才是強大代理真正需要的操作能力。

這篇論文是誰寫的？

論文全名：

Beyond Semantic Similarity: Rethinking Retrieval for Agentic Search via Direct Corpus Interaction
  • arXiv：2605.05242（2026-05-03 提交）
  • 作者包括 Dongfu Jiang、Wenhu Chen 等（從作者 X 貼文確認）

為什麼要重新設計檢索？

傳統 RAG 在靜態的大型語料上很有效。但代理式搜尋的需求不一樣，它需要：

  • 多跳推理（multi-hop reasoning）
  • 找出中間實體
  • 把零散的弱線索組起來
  • 看到部分證據後修正計畫

一次相似度查詢有幾個硬限制：

  • 一開始就被過濾掉的證據，後面救不回來
  • 很難同時表達精確的字面條件，或多個稀疏線索的組合
  • 把豐富的互動壓成固定的 top-k，本身就成了瓶頸

作者用了一個直觀的類比：

top-k 檢索像「請圖書館員幫你挑一小車可能相關的書」。

DCI 像「進到開放書庫的研究圖書館」——代理可以自己進去精確搜尋、看上下文、追線索、就地驗證假設。

對人類來說太慢，但對「代理 + 電腦」這個組合來說，grep + bash 又便宜又能組合。

實驗結果：同模型下 +11 百分點，成本降近三成

用同一個語言模型（Claude Sonnet 4.6）跑 BrowseComp-Plus（固定 100K 文件的深度研究基準）：

系統準確率成本
Qwen3-Embedding-8B 檢索器69.0%$1,440
DCI-Agent-CC80.0%$1,016

準確率 +11.0 百分點，成本 降 29.4%。

其他任務也大幅領先

  • 多跳問答（multi-hop QA）平均 83.0%，比最強的搜尋代理高 +30.7 百分點
  • 資訊檢索排名（IR ranking, NDCG@10）達 68.5，比 ReasonRank-32B 高 +21.5 百分點

不靠任何嵌入向量基礎建設

DCI 在 BRIGHT、BEIR 等多個資訊檢索基準上也大幅勝過稀疏（sparse）／稠密（dense）／重排序（reranking）所有基線——而且：

  • 不依賴任何嵌入模型
  • 不依賴向量資料庫
  • 不依賴檢索 API
  • 不需要離線建索引

這對動態變動的本地語料特別合適。

開源 lite 版（用 GPT-5.4-nano）在 BrowseComp-Plus 也達到 62.9%，超越許多用更強模型的傳統代理。

DCI 是怎麼實作的？

代理直接用一般命令列工具操作原始文字語料：

  • rg（ripgrep，快速搜尋）、grep、find、sed、bash 管線、檔案讀取、輕量腳本、正則表達式（regex）
  • 沒有嵌入、沒有向量資料庫、沒有檢索 API
  • 語料庫像程式碼庫一樣可以自由瀏覽、回溯、修正假設

開源最小實作：DCI-Agent-Lite ｜ github.com/DCI-Agent/DCI-Agent-Lite

基於 Pi framework + bash 工具 + 輕量上下文管理。

提示詞會引導代理優先使用 rg 等工具，並搭配上下文管理（截斷／壓縮／摘要，分多級控制長時程穩定性）。

為什麼 DCI 有效？

論文最有價值的發現不是「召回更多黃金文件」，而是：

「定位分數」高出一倍以上。

換句話說：

  • 傳統檢索器其實常常已經把有用證據翻給代理看了——但代理沒辦法把這些證據轉成下一步推理
  • DCI 一旦找到一份有潛力的文件，可以立刻在文件內部做高解析度的本地搜尋與驗證（這正是 grep 的強項）
  • 代理因此能像人類研究員一樣：提出假設 → 測試 → 讀局部上下文 → 修正查詢 → 驗證
  • 增益主要來自「把弱證據轉成可行動的證據」，不只是單純提高召回率

消融分析的三個重點

  • 簡單的 read + grep 介面已經抓到大部分增益
  • 開放完整 bash 還能再提升，但成本較高
  • 上下文管理的重點是「保留正確的工作狀態」，不是「保留最多文字」

限制：沒有免費午餐

DCI 在「找到第一份有用的錨點文件（anchor document）」階段比較耗資源。語料庫越大，廣度搜尋的成本越高。

它擅長搜尋深度（深度驗證），但搜尋廣度（找到第一個錨點）不會自動隨規模放大。

未來方向是混合式：語意檢索找錨點 + DCI 做深度互動 + 良好的上下文管理。

一句話收束

問題不再只是「哪個嵌入模型的 top-k 最好？」

而是「代理對知識應該擁有什麼操作？」

DCI 是把檢索重新設計成「高解析度互動層」的第一步——不是要全面取代檢索器。
