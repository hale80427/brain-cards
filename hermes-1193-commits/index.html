我家 AI 助理今晚一口氣吞了 1193 個更新

一個 Telegram bot、10 天累積、6 萬多行程式碼變化——從使用者角度看「個人 AI 代理」這條路長什麼樣

BLUF

我手機 Telegram 上有一個 bot，叫 Hermes。

它跑在我家 Mac mini 上，是個 AI 助理——可以幫我查筆記庫、發訊息給 Claude Code、做投影片、彙整 YouTube 影片。

它的「大腦」可以選 OpenAI 的 GPT-5.5 或 xAI 的 Grok 4.3。

今晚我跑了一次 hermes update，一次吞下 1193 個累積更新。上次更新停在 5/17，今天 5/27 一口氣補完。

這次更新刪了一萬多行舊程式、改寫了主對話流程的核心、修了我上週開始遇到的一個怪故障、還送了 3 個新功能。

這篇用「使用者會感受到什麼變化」的角度，記一下這次大跳版帶來的差別。

為什麼今晚會去更新？因為它先壞了

上週開始我發現一件怪事。對 Hermes 用 GPT-5.5 講話，它都會回我一個錯誤訊息 'NoneType' object is not iterable。

換成 Grok 4.3 就正常。我以為是 OpenAI 那邊餘額有問題，去他們網站確認帳戶配額其實還很多。

真正的原因比想像中有趣。OpenAI 在上週某個時間點偷偷改了 API 規格（API 是「程式跟程式之間溝通的接口」）。

他們的 ChatGPT Codex 後端回應結構有個欄位，從「會給內容」改成「可能是空的」。

問題是 Hermes 用的 OpenAI 程式套件（SDK，「別人寫好的工具包」）拿到「空的」就當「有清單」去走訪，直接炸。

這就是 NoneType 訊息的來源。

換成 Grok 4.3 沒事，是因為它走完全不同的網路路徑，跟 OpenAI 那條故障路線沒重疊。

「平台級事件」的特性：你的環境沒變、餘額沒少、設定沒動，但你的某個工具突然就壞掉。原因永遠在外面、永遠在公告之外、永遠來不及反應。

這次官方修法很妙：與其修 bug，不如不走那條路

如果你是 Hermes 開發團隊，你會怎麼修這個 bug？最直覺的做法是：

「OpenAI 那個欄位有時候是空的，我加一個檢查，空的就跳過。」

但 Hermes 的選擇更聰明：放棄 OpenAI 程式套件提供的「串流回應解析助手」，改成自己直接讀原始事件流。

原始事件流是 SSE（Server-Sent Events），伺服器主動推送訊息的方式。為什麼這個選擇更好？

  • OpenAI 程式套件是別人寫的，下次再出 bug 你還是被綁架
  • 自己讀原始事件流等於你掌握每一步發生什麼事
  • 一勞永逸——以後 OpenAI 再改規格，你只要對應自己的解析邏輯就好

這個哲學蠻像「自己種菜不買菜」——前期多花力氣，但獨立性換到手了。

下次菜市場斷貨也不會影響餐桌。

順帶這次更新還加了相關的「靜默卡死偵測」、「串流啟動計時警告」、「逾時設定」等近 10 條強化，把整個 OpenAI 鏈路重新加固一次。

你在 Telegram 端會感受到的 3 個變化

變化 1｜開機變快

  • 指令列工具啟動快了 63%——這是 update 訊息裡寫的數字
  • 對我來說：日常開機後 Hermes 服務啟動更快、定時排程觸發的對話延遲更低

變化 2｜對話穩定性提升

  • Telegram「打字中⋯」心跳變更穩——以前偶爾 Telegram 那邊顯示對方還在打字、其實 Hermes 已經卡住沒回應
  • 現在心跳會就地更新而不是不斷重發訊息
  • 對應的：bot 在跑長任務時的中間說明訊息持續開啟，會持續告訴你進度

變化 3｜切換模型更安全

  • 以前我用 /switch_model grok-4.3 切換模型時，如果重新登入失敗，會話狀態（session，「同一段對話的脈絡記憶」）會卡在半新半舊
  • 這次新增：切換失敗會自動退回原本的模型，不會留下殘破狀態，可以直接重試

新增 3 個內建工具 + 8 個現有工具更新

Hermes 的設計哲學是「核心薄、技能多」——核心程式碼少、能力靠各種獨立的「skill」擴展。這次內建 3 個新 skill：

名字用途
s6-container-supervision 容器服務監看。Container 是把程式包成「可攜帶獨立環境」的技術，s6 是其中一個監看工具。這個 skill 讓你從 Telegram 監看容器健康狀態
baoyu-article-illustrator 文章配圖。給文字段落、它自動生對應插圖。對我來說很有用——之前寫部落格都自己找配圖很費時
kanban-codex-lane 看板與 Codex 的整合。Kanban 是任務看板，Codex 是 OpenAI 的程式代理工具。這 skill 讓任務丟進看板、Codex 自動處理

另外 8 個既有 skill 也大幅更新：

  • polymarket（預測市場資料）
  • arxiv（學術論文搜尋）
  • xurl（X / Twitter 連結處理）
  • kanban-worker
  • comfyui（圖像生成工具）
  • maps
  • google-workspace
  • ocr-and-documents（文件文字辨識）

我自己改過的 4 個 skill 在這次更新中全部被保留。

這是 Hermes 設計上有趣的地方——它區分「上游內建版本」與「使用者覆寫版本」，不會無腦覆蓋。

其他值得知道的變化

新出網頁端 Dashboard 認證

以前 Hermes 主要透過 Telegram 跟指令列操作，網頁端不完整。這次新加完整的認證系統（共 15 個相關修改）——對團隊使用場景應該蠻關鍵。

Kanban 大幅進化

看板功能加了 68 個修改（45 個故障修正 + 23 個新功能）。

顯然這次版本的主推重點之一是把 Kanban 推到「可作為主力工作流」的程度。

Grok / xAI 也順手強化

Grok 4.3 的 OAuth（網頁授權登入機制）跟 slash command（斜線指令）也順手修了 12 條。雖然我這條鏈路沒壞，但跟著穩定一波也好。

安全強化

跟安全相關的修改有 23 條。具體訊息沒列細項，但顯然官方在持續加固。

這條「個人 AI 代理」路給我的 3 個反思

跑完今晚這次 update（外加為自己的客製功能補做手動整合，這部分明天再說），我有 3 個感受。

反思 1：開源 + 個人化 = 享受社群迭代速度 + 自己掌控資料

1193 個 commits（commit 是「一次程式修改紀錄」）是 NousResearch 這家公司的開源團隊 + 社群在 10 天內的累積貢獻。

如果我自己從零寫一個 AI bot，這 10 天會少掉幾百個別人已經寫好的功能。

但若我用商業 SaaS bot（例如直接用 ChatGPT app），我又沒辦法改它的系統提示詞、自己加擴充功能、整合自家工具。

「開源 + 跑在自己機器」是這兩個極端的中間選項——它把「社群迭代速度」跟「資料自主」這兩件原本互斥的事兼顧起來。

反思 2：但代價是要懂得保護自己的客製化

今晚我發現我 5/17 寫了一個叫 Phase 7.3 的功能一直沒進到 git。

這個功能讓某類安全攔截訊息能原文 forward 給用戶，不被 AI 改寫成自己的話。

如果裸跑 hermes update，那個改動會被 1193 個 commits 沖掉。

所以實際走「建專屬分支 + 提交保護 + update + 手動整合回主線」是個一小時左右的活。

「封版 ≠ 已進 git」——這個教訓正是我今晚補成永久備忘的原因。下次同情境就不會再踩。

反思 3：平台級故障在外面、你的工具壞了但你沒做錯任何事

這次 NoneType bug 教會我一個排錯紀律。

遇到平台 / 工具庫 / 雲端服務層的突發故障，先 5 分鐘搜社群（GitHub issues / Reddit / Twitter）驗證是不是大規模事件。

再決定要不要本機深挖。

我本機花 15 分鐘 6 步追到 SDK 那行 bug 觸發點。

後來才知道 Hermes 共同創辦人 Teknium 一早就在 Twitter 公告：

「OpenAI 改規格，跑 hermes update 就好」

本機深挖有獨家洞察價值（我追的過程順便發現「為什麼 Grok 沒事」的細節），但作為解 bug 的 step 1 ROI 不高。

收尾

如果 1193 個 commits 是 10 天的累積，那這條「個人 AI 代理」養成的路其實是：每天有一群人持續在改你身邊的工具，你要學會跟它共生。

差別在於——你選擇被動接收（商業 SaaS），還是主動參與（開源 + 個人化）。

後者麻煩、需要一點工程肌肉、偶爾要花一晚 debug；但回報是你的 AI 真的是「你的」。

今晚這次 update 是我第一次明確感受到這個 trade-off 的重量。值不值得？對我來說是。
