今天 evaluate skill 升了三次，做對的事比做多的事重要

BLUF

今天升了三個版本（v3.2.2、v3.3、v3.4-b）。中途試了一個 v3.4-a 失敗，rollback。過程中還遇到 git 異常刪 317 個檔案的災難。

重點不是「做了多少」，而是「保留下來的全部都是經得起 baseline 驗證的」。

起點：一支 39 分鐘的影片

早上看了 Anthropic 一支 YouTube 講座，題為《Evals for taste: Hill-climbing a slide-generation agent》。講者用「投影片生成 agent」當示範。一整套「為什麼要做 evals，怎麼設計，怎麼校準」的工程紀律。

影片的核心句很簡單：

Evals 是把「感覺好像變好」轉成「可行動訊號」的工具。沒有 evals，你只能在 production 失敗後手動 debug。

對照我手上的 evaluate skill（v3.2.1），我盤點出幾個影片有教、但我的 skill 還沒做到的事。然後就一條一條改。

下面講三個改動。每個改動都對應影片一個明確的教導。

改動一：先講理由，再給分

對應影片 36:30–37:30 段「reason-first ordering」

影片教什麼

LLM 有個內建特性叫「自迴歸生成」——簡單講就是它寫下一個字會被前面寫的字影響。

如果你叫一個 model judge 評分，它先寫出「總體 7/10」之後，後面寫推理時會不自覺地「合理化這個 7 分」。即使這份文件其實只值 4 分。

直覺類比：考試時老師如果先看到「答案是 B」，再看你的推導過程，他會傾向找理由支持 B。如果先看推導再看答案，他比較容易發現答案錯了。

我原本的問題

我的 evaluate 報告模板，總體評分表放在報告最開頭。LLM 寫到後面層次時，已經被自己寫下的分數鎖住了。

修法

把總體評分表從報告開頭，搬到最末尾。新模板強制走這個順序：

第 1 層命中 → 第 2 層機制 → 第 3 層盲點
  → 五維 sanity check → 綜合建議的優點/問題
    → 最後才填總體評分表

並在模板開頭加生成紀律提示，避免 judge 偷跑：

寫到第 6 步前不得在報告任何位置出現「總體 X/10」結論。

這就是 v3.2.2 的 reason-first ordering。對應 commit 09bee50。

改動二：給 judge 看「好 / 壞長什麼樣」

對應影片 33:30–36:30 段「judge needs anchored examples」

影片教什麼

講者展示一個荒謬例子：一份投影片沒有任何圖片，但 image judge 給了 5 分。

為什麼？因為 prompt 只寫「給 0 到 5 分」，沒給 judge 看「0 分長什麼樣 / 5 分長什麼樣」的具體範例。

直覺類比：請新進員工評酒。如果你只說「給 0 到 10 分」，他會亂給。如果你給他喝兩瓶——「這瓶 6 分、這瓶 9 分」——他評分就會穩定。

這叫 anchored scoring，給 judge 一個「錨點」對照。

我原本的問題

我的 evaluate skill 模板裡，只有描述性的 anchor：

10–8 分：高度可信
7–5 分：需要驗證
4–2 分：重大缺陷

這是講分數區間的意思，不是給 judge 看分數區間的範例。

修法

新增一份檔案 AI評估_分數錨點_v1.md。把我手上的校準集（calibration fixtures Q1/Q3/Q4）三個案例的特徵抽取，嵌進 prompt 流程。

例如「機制分 9 分長什麼樣」段：

命題式標題 + 「核心主張 / 推導邏輯 / 具體案例 / 跨域同構」四段論結構 + 多重約束第一性原理推導 + 跨域同構案例 + 邊界條件

「機制分 3–4 分長什麼樣」段：

BLUF 結構 + N 個結論編號 + 每個結論末固定加「為什麼重要：[一句話]」 + 大量元標記（DIRECT / INDIRECT / UNKNOWN）+ 大段事實列舉後接結論 + 形式重於機制

每次 judge 評分前，必須先讀這份檔案，把待評估文字跟特徵錨點逐欄比對，找最接近的描述對應的分數區間。

這是 v3.3 的 anchored scoring。對應 commit 21c4b24。

中場：跑全套 baseline 對照

對應影片 Step 7「重跑 eval，檢查改善與 regression」

兩個改動上線後，影片明確要求一件事：跑全套校準集對照，看新版有沒有把舊版搞壞。

我跑了三個 fixture：Q1（理想範例）、Q3（典型 AI 報告）、Q4（混合）。再加一份實戰素材（早上看的那支影片的 YouTube 摘要本身）。總共四份報告。

結果：

Fixture機制分語言積分對照 ground truth
Q19 ✅2 ✅全符合
Q33 ✅19機制對，語言低估了（應該 22–32）
Q49 ✅20 ✅全符合

Q3 語言分系統性低估了 3 到 13 分。

回頭找原因。Q3 是典型的 AI agent DeepSearch 報告風格。充滿 BLUF、編號清單、DIRECT/INDIRECT 證據等級標記。每個結論末固定加「為什麼重要：」句構。這些是結構層的 AI 味。但我的規則庫只覆蓋詞彙層（D 詞彙癌）跟句法層（G 翻譯腔）。沒有規則抓結構層。

這個發現很有價值，但也意味著要再升一版。我把規劃寫成 v3.4 的四個方向（v3.4-a / b / c / d），按 ROI × 改動量排序，準備一個一個動。

對應 commit 70feca9，五份 baseline 報告共 512 行。

改動三的失敗版：v3.4-a 嘗試補「不是 X 而是 Y」變體（後來 rollback）

動機

baseline Q4 報告發現一個漏抓。Q4 fixture 裡有句「不是某一家公司的策略選擇，而是 AI 原廠面對結構缺口必然演化出的四模塊」。這明顯是 C 類「二元對比洞察錯覺」句構，但 prefilter 沒抓到。

查正則表發現：C 類規則覆蓋三個變體——「這不是 X 而是 Y」「從來不是 X 而是 Y」「並非 X 而是 Y」。漏了最常見的無前綴版本。

嘗試的修法

加一條正則用「負向後查」排除已覆蓋的前綴：

r"(?<![這從並])不是.{1,25}而是"

技術上完全正確。改完跑全套 baseline 驗收。

Q1 誤抓的句子（全部是合法的事實澄清）：

  • 「AI 應用的上線複雜度不是傳統軟體的線性延伸，而是多了一整層獨有問題」
  • 「它的成本不是一次性購買而是按 token 計費」
  • 「不是寫碼層多了幾個函式，而是在工程之上多了一層」

YouTube 誤抓（全部是合法的重新聚焦）：

  • 「真正重點不是投影片，而是 agent engineering 的控制迴路」
  • 「不是調 prompt，而是換模型」

為什麼這些是 false positive？

因為 C 類二元對比的 AI 味，本質是語義層，不是句構層。

真 AI 味合法對比
「未來不是 AI 取代人，而是 AI 增強人」（廉價二分法，製造「有見地」假象） 「成本不是一次性購買而是按 token 計費」（純事實澄清）
「這不是技術問題，而是文化問題」（用二元簡化掩蓋多因素互動） 「真正重點不是投影片，而是 agent engineering」（重新聚焦讀者注意力）

判別點是對比的兩端是不是被強行對立，這需要語境理解，純正則無法區分。

決策：rollback

依影片 Step 7 紀律：

抓到 regression → rollback，不 push through。

修一個 +2 引入 +14 的 noise，ROI 顯著為負。把這次嘗試標為 ABORTED，rollback 規則，但保留試誤註解在程式碼裡，避免未來重蹈覆轍。

對應 commit 67f7766。

關鍵 lesson

如果 v3.4-a / v3.4-b / v3.4-c 三個改動 bundle 進一個 commit，會怎樣？我永遠無法定位 Q1/YouTube regression 是哪個改動造成的。

one-lever-at-a-time 紀律的真正價值，不在於 commit 訊息漂亮。而在於拉錯方向時，可以乾淨 rollback 一個 lever，不影響其他改動。

改動三的正版：v3.4-b 擴 I 類覆蓋 agent 報告免責語

設計思路（學了 v3.4-a 教訓）

v3.4-a 失敗根因是「人類也大量用此句構做合法澄清」。

v3.4-b 採對策：刻意只抓 AI agent 研究報告專屬的格式特徵。避開人類撰寫的決策文件、學術論文也會用的句構。

插曲：git 災難復原

中間還遇到一個怪事。commit 6a30b76 我只 git add 了三個檔案，pre-commit 用 git diff --cached --stat 確認也是三個檔案。但 commit 完跑出來顯示「317 files changed, 51280 deletions(-)」。它把整個 repo 的 git index 全清空了。

幸好 working tree 完整未動。檢查 .git/hooks/ 沒有任何 hook，git config 也沒有相關設定。原因至今不明，可能是 OS 或 git 在某種 race condition 下的異常。

修復流程：

git reset HEAD~1    # 把災難 commit undo（HEAD 退一步，working tree 不動）
# 重新 stage 三個檔案
# 採三段驗證流程：
git diff --cached --name-only    # 確認 staged 範圍
git ls-files --stage | wc -l     # 確認 index 檔案總數合理
git commit -m "..."              # commit
git show --stat HEAD | tail -10  # 立即驗證 commit stat 正常

第二次 commit 成功，3 files changed, 159 insertions(+)，tracked 檔案數從 319 → 320，正常。

從這次之後，每次 commit 後都跑這個三段驗證流程。

整體啟發

1. 紀律的真正價值會在「事情出錯時」才顯現

平常 one-lever-at-a-time 看起來像形式主義。為什麼不直接 bundle 三個改動一個 commit？

直到 v3.4-a 出事，才驗證它的真正價值——一個改動失敗了，可以乾淨 rollback，其他改動不受影響。

baseline 對照也一樣。平常跑來看似冗餘紀錄，直到 v3.4-a 規則 false positive 才驗證它是 regression 唯一防線。

2. 設計新規則時，先問「人類也用此句構嗎？」

v3.4-a 失敗，v3.4-b 成功，差別不在「正則寫得多漂亮」，而在「規則覆蓋的句構在人類文本中有多稀有」。

  • v3.4-a 的「不是 X 而是 Y」是人類大量使用的合法句構 → 一抓就誤抓
  • v3.4-b 的「研究截止：」「公開資訊不足以確認」是 AI agent 專屬 → 精準命中

寫規則時，先去看一份典型的人類撰寫文件（不是 AI 生成的）裡有沒有這個句構。如果有，就不該規則化。

3. 影片 Step 7「重跑 eval」是工程的，而非儀式的

我以前以為「跑 baseline」是好習慣但不是強制。今天親身驗證——沒它，v3.4-a 的 regression 會悄悄漏網，最後在某次評估真實文件時才被發現。到時要 debug「為什麼判錯」就會繞遠路。

baseline 對照不是「驗收 checklist 的某一項」，是「升版完成的前置條件」。

下次起點

今天累積到 v3.4-b，下次開新 session 可以接著動：

  1. v3.4-c（最高 ROI）：新增 J 類「結構性 AI 味」規則庫，4 個維度——子標題密度、清單覆蓋率、證據等級元標記、自定義固定模板偵測。預期完成後 Q3 加權總分從 12 → 22+，落入 ground truth 區間。這是修 Q3 系統性低估的根因動作。
  2. v3.4-d：新增中英混雜術語密度規則（Probability Mass / Brownfield 等專業詞中英並列密度過高即為 AI 味痕跡）。讓 Q4 的中英混雜部分從 LLM judge 手算變 prefilter 自動偵測。
  3. B1 新建 Q5 fixture：YouTube 摘要本身可作為標準素材（「中等機制 + 乾淨語言 + 結構性 AI 味」），補 anchor 表中間區間。

v3.4-c 涉及新類別架構（不只是規則擴展），複雜度遠高於 v3.4-b，建議單獨開 session 處理。
