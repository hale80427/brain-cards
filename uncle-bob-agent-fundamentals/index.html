對 agent 不要用 prompt 講道理，要用跑得起來的工具把它關進迴圈

Robert C. Martin（Uncle Bob）× Matt Pocock 直播訪談 · 56:39 · 2026-08-19 · 看原片
以下是中文整理與拆解，不是逐字翻譯；引號內為片中說法的中譯，後面的時間戳可跳回原片查證。
BLUF

他把「教 agent 寫好 code」從寫規則整個換成架檢查器。理由不是品味——他親眼看到 agent 被自己製造的爛 code 卡到繞圈、改一個壞一個，最後一隻直接說它處理不了了。

三個最硬的點：規則塞進 prompt 會失效（機制是 lost in the middle）；他挖出兩個 2000 年代「太貴而不能用」的老工具，因為 agent 不嫌無聊；人類的價值可以加在 agent 上，人類的紀律不行。

【機制】

1 · 說服他的不是 code 醜，是他看見 agent 開始打結

2025 年底，Robert C. Martin 開始認真用 agent 寫 code。第一個是早期的 Grok。它寫得出東西，但一直留下他所謂的「dog doo」——他得一路跟在後面清 04:50。

他當時的評語本身就是矛盾的：因為它快，所以有趣；因為它逼他一直清，所以讓他變慢 05:16。

真正翻轉他做法的是下一步。他刻意不清爛攤子、一路往下疊功能，然後看著 agent 改一個地方就弄壞另一個，修那個又弄壞下一個，開始繞圈。有一次 agent 直接放棄——他說原話不是那樣講的，但那顯然就是它的意思 11:59。

機制判斷 · agent 跟人一樣會被髒 code 拖垮。門檻也許高一點，但門檻仍然在。到了那個點，它不只是寫得慢，是會開始把事情越弄越糟然後動彈不得 11:30。

【機制】

2 · 你寫在開頭的規則，只要文件夠長就會被擠進沒人看的中段

他一開始也走塞規則那條路：把測試驅動開發（TDD）、Clean Code 的規矩寫成五到十頁的指示餵進去 12:55。

結果是 agent 把那些規則當成《神鬼奇航》裡的那種「規範」——比較像參考意見，看心情遵守 13:22。

他去查了機制，叫 lost in the middle（迷失在中段）。白話說：模型的注意力不是平均分配的，一段輸入的開頭與結尾權重高，中段被稀釋。所以你寫在最前面的規則，只要後面內容一長，它就被推進中段而失效——前三句可能還在，第 50、第 80 句已經沒了 14:26。

主持人補了一個同義說法，來自 Dex Horthy：context 有 smart zone 與 dumb zone，前段較聰明，越往後注意力越稀釋，「像每個字都在一間越來越擠的房間裡喊話，你聽不見訊號只聽見雜音」15:36。

他的結論 · 把初始 prompt 砍到最短，讓它擠得進高權重區；其餘一律交給事後跑的確定性工具。因為工具不會被稀釋掉——它要嘛跑過要嘛沒跑過 14:50。

【對照】

3 · 那兩個老工具當年不是無效，是人力太貴——而 agent 不嫌無聊

這是全片機制上最漂亮的一段。他挖出兩個 2000 年代初就存在、他當時試過又擱置的工具。

工具它做什麼當年為什麼被他擱置
CRAP score
05:53		 把測試覆蓋率、與每個函式的圈複雜度（cyclomatic complexity，白話說就是「穿過這個函式有幾條路徑」）混成一個分數。分數越高代表這個函式越糟。 他跑過一次，確實抓出一堆爛函式。但一個一個重寫函式、重寫測試，人做不完——而且東西當時是會動的，他覺得付不起這個代價。
Mutation testing
（變異測試）
06:49		 一支程式自動把原始碼裡的加號翻成減號、小於翻成大於、等於翻成不等於。每翻一次就跑一遍全部測試，預期測試該掛。沒掛，代表出現「存活的變種」——那就是測試的破洞。 同一個專案，測試跑一次四分鐘、要跑好幾百次，只能整夜跑。塞不進正常的建置流程。
Note：CRAP 片中只說「是個縮寫，我能說什麼呢」，沒有展開全稱，本文不代填。
Source：訪談 05:53–08:40。

2025 年底他想通的那句話，是整個轉向的支點：

這些傢伙很快，而且不在乎工作有多無聊，而且我叫它做它就做。

Robert C. Martin · 07:56

於是變異測試從整夜跑變成大約 30 分鐘，跑完 agent 自己去補上缺的測試 08:17。

他推到很激進的地方 · 他的目標是把系統做到「我完全不必看 code」09:02。理由不是偷懶，是分工：agent 對 code 很快，他自己很慢，所以他不打算把自己的慢強加上去 09:23。他改成看 CRAP 分數、抽查、跑一整批測試。

【機制】

4 · 他把工作切成五道關卡，每道換一顆乾淨的腦袋

這是他目前的實際做法。順序與分工如下 20:21–22:25。

多開幾隻的兩個好處，他講得很清楚

  • 可以平行跑——他說筆電同時撐得住的數量遠不只三隻 19:26。
  • 每隻只做一件事，context 就受控——lost in the middle 沒那麼嚴重，於是頂端能多塞幾條規則而且真的被遵守 19:34。
  • 附帶手法：讓 agent 出生 → 做完 → 死掉，下一隻拿到全新的 context 19:53。

代價他也講了 · 啟動成本高——一隻 agent 光起來就 10 到 15 秒，起來之後還要重新摸清整個 context 20:06。而且他明說這套正在犧牲生產力換品質，只是他還沒找到那個換不下去的臨界點 17:28。

他自己給的讀數是 4 到 5 倍，但那是體感不是實驗

同一件事：單一 agent 五分鐘做完，但品質可疑；走完這五關約一小時；人來做約半天 22:29。他算成 4 到 5 倍生產力，而且品質比人願意給的更高。

先別當數據用 · 這是他的自述，沒有量測方法、沒有對照組，片中也沒說是什麼專案、什麼語言、多大的 codebase。它是一個實務者的體感，不是一個實驗結果。

【機制】

5 · context 有一條軌跡，而軌跡會污染後面每一句話

主持人先給了說法：一個 session 的走向會自我延續。你叫它測一次畫面，之後每一次改動它都會回去測畫面。清掉軌跡的唯一辦法是清掉 context 23:11。

Uncle Bob 用一個跟程式無關的例子接住，這是全片最好懂的一段：

你正在跟模型聊咖啡怎麼沖。旁邊有人走過，在講他昨天看的連續劇——那段話進了 context。你沒放進去，是路過的人放的。從那之後，所有關於咖啡的回答都會沾到那齣連續劇。模型分不出來。

Robert C. Martin · 24:03（依片中說法中譯）

他的推論：只要 context 內部保持一致、方向不亂，那些誇張的幻覺就不太會發生 24:54。

同一個機制他直接搬去論證模組化 28:33：一個模組如果什麼東西都往裡塞，agent 進去會不知道自己在幹嘛；切乾淨了，每個模組自己有一條軌跡，它就不會被裡面的雜訊搞混。

【複盤】

6 · 架構是他到現在唯一還沒自動化成功的一塊

直到訪談前一個月，模組結構都還是他手動處理：叫 agent 建完東西，再回頭審問它「這裡結構長怎樣、模組之間怎麼講話」——然後被答案嚇死，再自己設計模組切法丟回去重來 26:06。

他為此做了兩個東西：

  • 架構檢視器（他讓 agent 幫他做的）：畫出 UML 式的模組圖與依賴流向，可以點進子模組、一路點到原始碼 26:55。
  • 依賴規格檔＋檢查器：明文定義誰可以依賴誰、依賴該往哪個方向流，寫成一份 agent 不能違反的規格。末端跑檢查器，違反就得自己修——通常是反轉依賴、插一層介面、或把模組切開 27:34。

他明講的失敗 · 「我現在正在試能不能把這塊也自動化，目前運氣不太好」28:08。這是全片唯一一處他主動說自己還沒做到的地方。

模組切好，agent 才不會在裡面迷路

他的論證跟乾淨 code 是同一個：切得好、介面有紀律的東西，人腦抓得住，因為人是靠分艙來理解的。模型是照著人建的，所以也吃這套 28:33。

主持人補上 John Ousterhout 的 deep module（深模組：介面窄、內部藏得深）為什麼特別適合 agent——模型可以只讀介面就動作，不必讀實作 30:04。Uncle Bob 同意，並補了一句重要的但書：

這既是優勢也是危險 · 只讀介面不讀實作能成立的前提，是底下的 code 真的跟介面一致 30:34。他還提到模型會去讀測試，用測試來理解系統到底在做什麼。

【對照】

7 · 人類的價值可以搬過去，人類的紀律不行

這是全片最值得單獨記住的一段區分 35:01。

最有說服力的一個觀察 · 就算他明確下令要高紀律的 TDD，agent 每次都會滑回「先寫函式再補測試」那個節奏 34:56。他的判斷是：那大概就是它適合的方式。

他自己補的但書 · 他跟 agent 討論過「CRAP 設 6 合不合理」，agent 說大概可以。然後他馬上補一句：你不能相信任何跟 agent 的辯論 33:37。

【對照】

8 · 他認為 spec-driven development 大概不會成功

他把「先把規格寫到極致再交給 agent」直接對應到 1970 年代的瀑布式開發，而敏捷就是對那件事的回擊 36:16。

他自己試過，訪談那週還在試，結果一律是災難，而且失敗形狀固定：計畫寫好了，agent 跑起來你才發現有些事你沒想到、而它們沒你有智慧，於是它們半調子地衝出去，你得喊停、回捲、重寫計畫、重跑 37:09。

agent 特別會助長這個陷阱 · 「agent 超愛寫計畫。天啊它們有多愛。它們會把計畫寫得華麗、漂亮、細節齊全」39:13——然後在收尾的時候垮掉。

他用來說服人的比喻，是本片最好的一段類比

如果蓋房子的每一次修改都只要一塊錢——包含打地基、上屋頂在內，每改一次都是一塊錢——你還會先付幾千塊給建築師畫出完美藍圖，再花一塊錢叫承包商一次蓋好嗎 39:59？

變更的成本已經跌到接近零，接近到我認為不可能再更低了。那你為什麼還要做昂貴的前期規劃？為什麼不就一直改、改到看起來對為止？

Robert C. Martin · 41:06（他自己補了一句：這個預測我大概會輸）
【機制】

9 · 規格是消耗品；工具不要下載，讓你的 agent 讀完自己造一個

主持人問他會不會把規格存進 repo。不會——規格是短暫的，改一改就丟 43:00。

他順手點出一個真正的結構空缺：以前原始碼就是最終規格，因為那是人寫的。現在原始碼還在，但寫的人不是我們了。很多人感覺到的失落，來源就在這裡 42:53。

他現在的做法是反過來的：不先寫規格定義我要什麼，而是看最終產出，然後說「那個就是規格」 43:21。

他把 CRAP 工具（Clojure、Java、Go 版）、變異測試器、他自己的 agent harness 都放出來了，但他的建議是：

別下載那些東西。我是寫給我自己用的。你該做的是把你的 agent 指過去，讓它讀，然後幫你造一個你自己的。

Robert C. Martin · 43:52

順帶講到的一個不對稱 · 你丟一份龐大規格給人看，命中率也許 20%，可能 5% 更實際；丟給 agent，它真的會讀完。反過來——agent 寫的東西，人不讀。它們期待我們讀完它們寫的每個字，而我們就是不讀 44:16。（那兩個百分比是主持人隨口舉的，不是引用研究。）

【複盤】

10 · 新人要在哪裡長出戰略能力——他說他沒有完美答案

框架借自 Ousterhout 的戰術 vs. 戰略：戰術是地上打仗的士官，戰略是指揮戰爭走向的將領 45:46。兩人同意 agent 在戰術上很強、在戰略上很爛 46:01。問題是 AI 把戰術層吃掉了，新人要在哪裡長出戰略。

他的路徑，講的時候反覆說「我不知道，大概是這樣」：

  1. 先真的寫 code，寫一年左右——這樣你才知道 agent 在處理的是什麼 46:58。
  2. 進公司後，前幾個月被當成一隻 agent 對待 47:29——帶你的人給你跟 agent 一樣的任務，用一樣的確定性工具卡你。你會非常沒有生產力，但學到非常多。走完這道關卡，也許才能被信任去管一隻自己的 agent。
  3. 不能完全失去 code。他拿十年前的老建議類比：沒寫過組合語言的人，該花一個週末寫組合語言，否則你活在幻想世界裡，底下還有你不懂的魔法 48:17。
  4. 去讀沒人讀的老書：Tom DeMarco、Ed Yourdon、《The Pragmatic Programmer》51:38。要自己過濾掉過時的部分——很多寫於 70、80 年代——但那正是這些教訓被學會的年代。

他自己是怎麼發現 agent 出問題的（這題答得最好）

早期他是看 code 看到爛東西。但他說那不是重點。重點在下一步：他看著 agent 在掙扎，而他認得那個掙扎，因為他自己掙扎過 50:59。

問題就在這裡：新手進來，認不出那個掙扎。

Robert C. Martin · 51:18

主持人補的樂觀面 · 戰略能力的回饋迴圈傳統上很長——你犯的錯九個月後才炸，跳槽跳得快的人可能永遠學不到。agent 把這個迴圈壓短了，你有機會更早看到自己的錯 50:40。

【機制】

11 · 基本功還重要，因為它是把複雜度整理成「可以被想」的形狀

他引 Dijkstra（他自己先聲明「我大概會引錯」）：軟體是人類嘗試過最複雜的事 53:36。

所以基本功的角色是：把複雜度組織成一個可以被構想的形狀——不只是人可以構想，模型也可以。因為我們的模型本來就是照人建的 53:46。

對那些說基本功不重要的人，他的話沒有客氣：他們會學到的，而且是用痛的方式學，而且不會花太久。可能比他以為的久一點，因為 agent 確實不錯——但他撞過那面牆，所以他知道牆在那裡 54:14。

你丟掉的那些規則，一年後你會從地上撿回來、拍掉灰塵，然後想起你為什麼需要它們。

Robert C. Martin · 55:37

主持人收在抽象層的歷史上：二進位 → 組合語言 → 編譯器 → 現在是模型。每一層被跨過的時候，下面那層的人都說「這下全毀了、我們沒工作了、五歲小孩都能寫 code 了」——而當年他們講的還是二進位 55:00。最後他丟了柏拉圖那個「文字會讓人變笨」的老典故當註腳 55:48。
