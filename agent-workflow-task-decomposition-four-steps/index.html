把任務拆成 Agent 工作流的四步框架

BLUF 這支影片的核心不是多寫 prompt，而是一套四步方法論：把腦中的 Human SOP 拆成 agent 可跑、可觀察、可修復的 workflow。從格式標準化、任務拆解、雙向迭代，到工具整合與人工確認節點。

影片的核心問題

大多數人用 AI 都卡在同一個地方：task 太大、太模糊，agent 跑起來像黑箱，出錯了不知道從哪修。

這支影片的答案不是「換更強的模型」，而是把你腦中的 Human SOP（標準作業程序）拆成 agent 可跑、可觀察、可修復的 workflow（工作流）。

Mega Agent 的三個死穴

講者用比喻說明：請人打掃，就算幫手很聰明，沒定義「乾淨」是什麼，他也不知道你在意地板不黏還是水槽不能有碗。

問題不在智力，而是「隱含標準沒有外顯」。Mega agent（大型全能代理）短期 demo 看起來不錯，但上線有三個死穴：

  • 不可觀測：不知道中間發生了什麼。
  • 不可修復：出錯只能整包重寫。
  • 不可控：高風險動作可能被自動執行。

四步框架：把 Human SOP 轉成 Agentic Workflow

Step 1：格式標準化

把散文式 SOP 轉成 agent 能讀的規格，三個重點：

  • 參數化：不寫死固定值，改用 mode、temperature 等參數讓 SOP 變成模板。
  • 規則強度分級：用 RFC 2119 的 MUST、SHOULD、MAY 區分硬規定、建議、可選。
  • 結構化格式：用 Markdown 拆 Parameters、Steps、Error Handling 區塊，人與 agent 都能讀。

Step 2：任務拆解與 Artifact 串接

把大任務拆成 pipeline（流水線）步驟。每個節點都要有 input（輸入）、output（輸出）、成功標準，能獨立執行與 debug。

節點之間靠 artifact（中介資料）串接。例如分類 agent 輸出 JSON，列出白色衣物、深色衣物、精緻衣物。

下一個 agent 讀這份 JSON，決定洗衣模式。這不是心電感應，而是清楚定義的資料格式。

Step 3：雙向開發，把默會知識翻出來

講者說這一步最重要。SOP 的本質是把默會知識（Tacit Knowledge）轉成文字規則——那些藏在人腦與習慣裡、平常說不清楚的判斷標準。

直到 agent 跑錯，你才會發現自己漏寫了判斷標準。所以先跑粗糙版，觀察錯誤，再補規則。

agent 把含棉衣物高溫烘乾縮水了，就補「含棉量超過 80% 不可高溫烘乾」的規則。

幾輪後常見情境趨穩，edge case 才交人工確認。

「速度的關鍵不是寫得多完美，而是迭代得有多快。」

Step 4：整合工具與設人工確認節點

SOP 寫得再漂亮，沒接到真實工具就只是文件。要對接公司內部系統、資料庫、API、ticketing system 等。

MCP（Model Context Protocol，模型上下文協定）像 AI 世界的 USB-C，讓不同 agent 主機用同一套介面調用工具與資料。

最後在高風險節點設 human-in-the-loop checkpoint（人工確認點），agent 必須停下來等人確認再繼續。

「不是一台失控的機器，而是一個人類掌舵、agent 執行的系統。」

實際案例：公司內部請求分類

公司每天從 Slack、Email、表單收到雜事：權限申請、發票報帳、新人 onboard（入職流程）。原本靠人工掃描、判斷、指派。

轉成 agentic workflow 後，拆成兩個 skill（技能單元）：

  • internal request triage（請求分類）：輸出 JSON，含類型、優先級、負責部門、指派對象。
  • internal request reply drafting（回覆草稿）：讀 JSON，產出回覆草稿。

跑幾輪後，修正 priority 全判 Medium、assignee 指到離職員工等問題。

涉及超過五千塊財務或 admin 權限變更時，設人工確認節點強制暫停。

一句話帶走

「你不是在學怎麼用 AI，而是在學怎麼設計給 AI 用的工作流。前者很快會過時，後者越來越值錢。」

好 Workflow 的七個判準

  • input 明確。
  • output 明確。
  • artifact 格式明確。
  • 單一節點只做一件事。
  • 出錯時能定位是哪個節點壞掉。
  • 修改一個節點不牽動整條流程。
  • 高風險動作前停下來問人。
